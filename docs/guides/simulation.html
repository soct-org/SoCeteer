Running a Design in Simulation

Run the exact generated SoC as a Verilator simulation — a cycle-accurate model of the design's Verilog, no board required. The program's console I/O appears on your terminal, and the simulator can record waveforms of every signal. Needs Setting up SoCeteer; launcher commands run as described there.

1. Generate the design and build the simulator

One target does both — it emits the design for simulation, then configures and builds the sim/ CMake project against it:

sbt "runMain soct.SOCTLauncher --target verilator.build"

The result is workspace/<design>/sim/build/sim-build/simulator, an executable containing the whole SoC. Without options the default design is generated; --config and --with-config choose others, exactly as in From Design to Bitstream.

The two steps also run separately: --target verilator emits only, and the sim/ project configures like any other software project (Setting up SoCeteer, step 4) — with -DCMAKE_BUILD_TYPE=Release, which the combined target uses as well. A debug simulator runs many times slower.

2. Build a program to run

The simulator runs the same bare-metal ELFs a board would. Point the binaries/ project at the generated system and build one — hello-hart is the smallest:

cmake -S binaries -B <build-dir> -DSOCT_SYSTEM=workspace/<design>/sim/SOCTSystem.cmake
cmake --build <build-dir> --target hello-hart

Built ELFs land in the workspace's elfs/ directory.

3. Run

workspace/<design>/sim/build/sim-build/simulator workspace/<design>/sim/elfs/hello-hart.elf

The simulated SoC boots the way the hardware does — through the boot ROM, with the design's own device tree — then loads and runs the ELF. The program's output prints to the terminal, and when it exits, the simulator reports the exit code and finishes. Expect seconds for a hello-world: simulation runs at a tiny fraction of hardware speed, so it suits programs and system bring-up, not long workloads. --help lists the simulator's options (logging, reset cycles).

After regenerating a design, rebuild the simulator (re-run --target verilator.build) before simulating again: the boot ROM and its device tree are compiled into the simulator binary, and a stale one boots the old design's ROM — typically hanging early in boot.

4. Waveforms

Only when you want to inspect signals; tracing slows the simulation considerably and the files grow large quickly.

Tracing is a build-time switch of the sim/ project: configure it with -DVL_TRACE=1 and rebuild. That records two levels of hierarchy; -DVL_TRACE_DEPTH=<n> reaches further down, at the price of file size — signals inside the core need it. The simulator then writes dump.vcd next to where it runs — --vcd-file=<path> chooses another location — and any VCD viewer (for example Surfer) opens it.

For what the simulator models and how the boot flow works, see the Bare-Metal Programs and Linux system pages.
