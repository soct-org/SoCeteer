Monitor & Linux Programs

The full run: a video design on the board, Linux booting from SD, a DisplayPort monitor with a USB keyboard as a self-contained terminal, images on the screen, and persistent storage on the card. Relies on Setting up SoCeteer (including its Linux-development step) and From Design to Bitstream (or its remote variant). Steps 1–3 run on the development machine; steps 4 onward happen on the board's consoles.

1. Generate and build the video design

sbt "runMain soct.SOCTLauncher --target vivado.bs --board ZCU104 \
  --config soct.RocketB2 --with-config soct.WithIncoherentVideoStream --with-config soct.WithL2Cache \
  --ext-mem-part <DIMM-part> --vivado <path-to>/vivado --vivado-parallel 8"

This is the build flow from From Design to Bitstream; that guide explains how to fill in the placeholders and how long the build takes. The --with-config additions put the video pipeline into the design — the incoherent variant plus L2 is the right choice for a console, since its display cannot be starved by CPU load; DisplayPort Video compares the variants. The build's workspace is workspace/RocketB2-64-l2-video-nc/ZCU104/; when it finishes, program the bitstream onto the board.

2. Build the shell image

On your computer, in the binaries/linux project (CLion: build the target; terminal:)

cmake -S binaries/linux -B build-linux \
  -DSOCT_SYSTEM=workspace/RocketB2-64-l2-video-nc/ZCU104/SOCTSystem.cmake
cmake --build build-linux --target shell-boot-elf

The first build compiles the entire Linux kernel — expect tens of minutes; rebuilds after that are quick. The result is shell.BOOT.ELF in the workspace's elfs/ directory: firmware, kernel, the design's device tree, drivers and a BusyBox userspace in one file. It must match the flashed bitstream — rebuild it whenever the design changes.

Next to it lies shell.board.BOOT.ELF: the same image without an embedded device tree — it boots with the description baked into the bitstream, which cannot disagree with the flashed hardware. Prefer it whenever you are unsure the board's bitstream matches your current workspace; the embedded flavor is for iterating on the device tree itself.

3. Prepare the SD card and cables

  • Copy shell.BOOT.ELF onto a FAT-formatted SD card renamed to BOOT.ELF, at the top level — that exact name is what the boot ROM looks for.
  • Copy a few images (PNG/JPEG) next to it, for step 7.
  • Insert the card into the board, connect the DisplayPort monitor and a USB keyboard.
  • Connect the serial console — a text terminal into the SoC over the board's USB cable. Open it at 115200 baud, e.g. screen /dev/ttyUSB1 115200.
Which serial device? The board's USB-UART bridge shows up as several ports — compare ls /dev/ttyUSB* (macOS: /dev/tty.usbserial-*) before and after plugging the board in, and try them at 115200; the right one prints text during boot. If the port is missing or silent: close the Vivado Hardware Manager (it holds the port), avoid USB hubs, and on Linux udevadm trigger re-creates a vanished device.

4. Boot

After a power-up, the processing system must be initialized (psu_init) before Linux boots — without it the monitor and USB stay dead. From Design to Bitstream, step 3, covers it.

Power-cycle the board (or press its reset button). The boot ROM loads BOOT.ELF from the card; boot ends in a banner on both consoles: the serial terminal, and the monitor, which renders the Linux console. The USB keyboard types into its own independent shell on the monitor. The prompt reads ramdisk@ZCU104: the system is RAM-only, nothing survives a reboot yet.

Warm reboots (reboot, the reset button) reset the SoC but not the processing system, which keeps running with live state — USB may come back dead, and a power cycle plus psu_init is the cure. The boot banner lists the known quirks of whatever hardware the image finds itself on.

The shell is BusyBox — the usual commands (ls, mount, vi, dmesg) — plus SoCeteer's own helper programs; the banner lists them. Steps 5–7 are those helpers.

5. Video modes: fbmode

fbmode switches the monitor's resolution and refresh rate:

fbmode            # show the current mode and a numbered list to pick from
fbmode 6          # switch to list entry 6
fbmode --custom 1600 900 60   # any other geometry

Confirm a switch by pressing y within 10 seconds, otherwise it reverts — the protection against a mode the monitor cannot display. What modes the design can produce: DisplayPort Video.

6. Persistent storage: soct

soct creates and enters a persistent environment on the SD card (or a USB stick) — the answer to the ramdisk prompt:

soct              # lists SD/USB devices and what they hold, then enters or creates

Inside (prompt soct@ZCU104), files under /home/soct and the shell history survive reboots, and the card's FAT — the images from step 3 — is at /media/<device>. Leave with exit: when the last session leaves, everything is unmounted and a message says the card can be pulled. Do not pull it before that message; if it does not come, the printed list names the console still inside.

7. Images on the monitor: fbimg

fbimg shows an image file (PNG, JPEG, BMP, GIF) on the monitor:

fbimg /media/mmcblk0p1/photo.png

It holds the screen until any key or Ctrl-C — from either console.

Without a monitor, everything except fbmode/fbimg works identically over the serial console alone — the video design still boots fine.
During development the SD step can be skipped: with the flash variables set (Remote Development), cmake --build build-linux --target shell-flash loads the image over JTAG — the card is then only needed for soct storage.
