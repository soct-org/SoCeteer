Remote Development

Bitstream builds need a large Linux machine; the checkout, IDEs and editing stay local. This guide connects the two: a build server (a lab machine or shared server) runs Vivado over SSH, driven from the local checkout. Assumes Setting up SoCeteer.

1. One SSH config entry

SSH has a config file, ~/.ssh/config on your computer, where a Host entry gives a machine a short name plus how to reach it. SoCeteer addresses the build server by that name — it is what --ssh-config takes. Create (or extend) the file:

Host fpga-server
    HostName 192.168.1.50        # its IP address, or a hostname if it has one
    User <your-login-on-that-machine>
The server side has three prerequisites: an SSH daemon (sshd) running, a firewall that lets SSH through (port 22 by default), and a POSIX/bash-compatible login shell — the launcher drives the server with shell commands. The Arch Wiki's OpenSSH page covers installing and enabling sshd and the firewall side.

Test with ssh fpga-server: it should open a shell on the server without a password prompt (otherwise set up SSH keys first). Everything below uses the name fpga-server; substitute accordingly.

2. Build the bitstream remotely

Take any build command from From Design to Bitstream and add the remote flags. Note that --vivado now names the executable on the server, not the local one:

sbt "runMain soct.SOCTLauncher --target vivado.bs --board ZCU104 ... \
  --remote-dir soct-work --ssh-config fpga-server --use-remote-vivado \
  --vivado <path-on-server>/vivado --vivado-parallel 8"
Unsure where Vivado lives on the server? ssh fpga-server which vivado, or look under its Xilinx installation root — vivado and the xsdb used below sit in the same bin/ directory.

--remote-dir is a directory on the server, relative to the home directory there; the launcher creates it, syncs the generated project over and launches the build detached on the server — it prints the log path and a follow command, and disconnecting locally does not kill the run. When the log reports the bitstream done, pull the results back into the local workspace by re-running the same command with --sfr (sync-from-remote) in place of the build target.

3. Flash binaries remotely

When the board is connected to the server, programs are flashed through it too. This part is CMake, not the launcher: point the build tree at the server's xsdb once (in CLion: the CMake options field; terminal: the configure command), and every program's <name>-flash target uploads the ELF and flashes it from there:

cmake -S binaries -B build -DSOCT_SYSTEM=<workspace>/SOCTSystem.cmake \
  -DSOCT_FLASH_HOST=fpga-server \
  -DSOCT_FLASH_XSDB=<path-on-server>/xsdb

cmake --build build --target hello-hart-flash

The same variables work on binaries/linux, where each boot image gets a <name>-flash target (e.g. shell-flash) — booting Linux without touching the SD card. The variable reference and flash preludes (extra TCL before loading, e.g. programming the bitstream first) are on the Binaries page.

The board's serial console cannot cross SSH by itself — attach to it on the server, e.g. ssh -t fpga-server screen /dev/ttyUSB1 115200. Monitor & Linux Programs shows how to find the right ttyUSB device.
