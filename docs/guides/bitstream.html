From Design to Bitstream

Generate a design for an FPGA board and let the launcher drive Vivado to a bitstream — the file that configures the FPGA with the design. Needs Setting up SoCeteer and an AMD/Xilinx Vivado installation. Launcher commands run as described there: in a terminal, or as the program arguments of the IntelliJ run configuration.

1. Generate the design

A design is a core config plus additions, generated for a specific board and the memory module actually inserted in it:

sbt "runMain soct.SOCTLauncher --target vivado.bd --board ZCU104 \
  --config soct.RocketB2 --with-config soct.WithIncoherentVideoStream --with-config soct.WithL2Cache \
  --ext-mem-part <DIMM-part> --vivado <path-to>/vivado"
Filling in the placeholders:
  • --board — a registered board name (currently ZCU104, VCU118; the README lists them). The VCU118 has no 3.3 V PMOD bank for the SD card, so it needs a configuration without the SD controller and an explicit --bootrom msip-boot — generation says so when either is missing.
  • --ext-mem-part — the part number, read off the label of the memory module inserted in the board's DIMM slot. If omitted, the board's factory module is assumed; unknown parts must be added to the registry — see FPGA Memory & Custom DDR4.
  • --vivado — the vivado executable inside your installation, e.g. /opt/Xilinx/Vivado/2025.2/bin/vivado.
  • --config / --with-config — fully-qualified Scala config names from the soct package (cores like soct.RocketB1, additions like soct.WithL2Cache); --help shows the defaults.

Generation takes about a minute and creates workspace/<design>/<board>/ — the design name encodes config and additions, e.g. RocketB2-64-l2-video-nc — holding the Vivado project, the device tree and the SOCTSystem.cmake the software builds are pointed at. --target vivado.bd generates the project without building it, useful for inspecting the design in the Vivado GUI first.

2. Build the bitstream

Same command, different target, plus parallel jobs:

sbt "runMain soct.SOCTLauncher --target vivado.bs --board ZCU104 ... --vivado-parallel 8"
TargetResult
vivado.bdproject + block design only
vivado.syn…then synthesis
vivado.bs…then the bitstream

The launcher returns after a minute; the build itself continues detached in the background, and the launcher prints the log path plus a ready-made command to follow it. Expect between half an hour and a few hours depending on the design and the machine; write_bitstream completed successfully at the end of the log marks completion.

--vivado-parallel sets how many jobs the run may use; without it the build runs single-jobbed.
Without a local Vivado installation (or a machine too small for it), the same commands run the build on another host — see Remote Development.

3. Program the board

Open the workspace's Vivado project and program the bitstream with the Hardware Manager (or your usual xsdb flow).

On MPSoC boards (ZCU104), one more step after every power-up, before booting software: run the psu_init initialization (a TCL script executed through xsdb). It configures the processing system — DisplayPort and USB live there and stay dead without it. The script is produced by the Vivado project's hardware export, so after a remote build it sits on the build server; copy it somewhere a regeneration will not delete. Flash preludes run it automatically with every JTAG load — see the Binaries page.

From here on it is software: the boot ROM inside the bitstream loads BOOT.ELF from the SD card, and JTAG can load ELFs directly — the Binaries page covers both, and Monitor & Linux Programs is the full worked run.
