Setting up SoCeteer

From nothing to a generated design and working IDE projects. Follow it top to bottom once; every other guide assumes it. No prior experience with sbt, CMake or projects of this size is assumed.

On Windows, read SoCeteer on Windows first: it lists what differs, what is limited, and the steps to take before cloning.

1. Install the tools

In a terminal (all of this is on your own computer):

# Ubuntu/Debian:  sudo apt-get install git cmake ninja-build device-tree-compiler flex bison
# macOS:          brew install git cmake ninja dtc flex bison

And the two IDEs, both from JetBrains:

  • IntelliJ IDEA with the Scala plugin — for the hardware side (the design generator is written in Scala).
  • CLion — for the software side (everything that runs on the generated SoC is C, built with CMake).
Both IDEs are free for non-commercial use, and students get the whole JetBrains toolbox free (jetbrains.com/community/education). The IDEs are optional — every step below also has a terminal form.

2. Get the code

git clone --recurse-submodules https://github.com/soct-org/SoCeteer.git
cd SoCeteer

--recurse-submodules matters: the repository pulls in the CPU generators (Rocket Chip among others) as git submodules.

3. Run the launcher once

The launcher (soct.SOCTLauncher) is the program that turns a design description into everything else — Verilog, device tree, Vivado project. The guides always write launcher invocations in their command-line form:

sbt "runMain soct.SOCTLauncher <options>"

Pick one of the two ways to run these, and read every launcher command in the guides accordingly:

  • Terminal: paste the command as-is, in a terminal at the repository root. sbt is Scala's build tool — install Java 11+ and SBT first. The first run downloads the Scala toolchain and takes several minutes.
  • IntelliJ: File → Open the repository root; IntelliJ recognizes the sbt project and imports it (the first import also takes several minutes). Then create a Run/Debug configuration of type Application: main class soct.SOCTLauncher, and the <options> part of a command — everything after runMain soct.SOCTLauncher — goes into the Program arguments field. Pressing Run is the IDE equivalent of the command; keep one configuration per design you work on.

Run the launcher once without options to verify the setup: a new workspace/<design>/<target>/ directory appears in the repository. The file to remember in there is SOCTSystem.cmake: it describes the generated system (memory map, cores, devices), and every software build in the next step is pointed at it. --help lists all launcher options.

Two launcher behaviors worth knowing before you rely on the workspace. Every run also refreshes SOCTSystem-latest.cmake at the repository root, a link to the system file it just generated — the software projects fall back to it when no -DSOCT_SYSTEM is given, so with a single design you can skip that option entirely. And a run regenerates its workspace directory: files you placed there by hand (scripts, notes) do not survive the next generation — keep your own files outside workspace/.

4. Open the software projects

The software side is not one big project — it is separate CMake projects, each opened on its own (in CLion: File → Open on the directory):

Project directoryWhat it buildsConfigure with
binaries/bare-metal programs, boot ROMs -DSOCT_SYSTEM=<workspace>/SOCTSystem.cmake
sim/the Verilator simulator -DCMAKE_BUILD_TYPE=Release -DSOCT_SYSTEM=<workspace>/SOCTSystem.cmake
binaries/linux/kernel, drivers, Linux userspace -DSOCT_SYSTEM=<workspace>/SOCTSystem.cmake (see step 5)

Where the “Configure with” column goes:

  • CLion: into the CMake options field of the CMake profile (Settings → Build, Execution, Deployment → CMake). CLion then configures the project by itself.
  • Terminal: after cmake -S <project-dir> -B <build-dir>, then build with cmake --build <build-dir> --target <name>.
<workspace> is the directory step 3 created: workspace/<design>/<target>/ under the repo root. Each generated design has its own, so the software projects follow whichever design you point them at. With several designs generated, prefer the explicit option over the SOCTSystem-latest.cmake fallback — the fallback follows whichever design was generated last (the configure warning names the system file it resolved to). Avoid build-directory paths containing spaces or commas — the Linux project refuses them at configure time.

5. Linux development

Only needed when you build Linux things (the kernel, drivers, Linux userspace programs, boot images) — skip it otherwise, whichever path you use. The kernel and firmware sources are not submodules; clone them once into place: 
git clone --depth 1 --branch v7.2-rc3 https://github.com/gregkh/linux.git binaries/linux/linux-stable
git clone --depth 1 https://github.com/riscv-software-src/opensbi.git binaries/linux/opensbi
Newer versions may work; these are the tested ones. Then open (or configure) binaries/linux like the other projects in step 4. Configuring lists every tool still missing (LLVM, GNU make, host tools) with the install command for each — details on the Booting Linux page.
Platform note: the firtool binary Chisel needs is x86_64-only — on Apple-silicon macOS install Rosetta first (softwareupdate --install-rosetta --agree-to-license). Windows specifics are in SoCeteer on Windows.
